# contract/

The one place for everything the TypeScript reference and the native port are
both tested against. The TypeScript packages produce it; the Swift port replays
it and must answer byte for byte the same canonical JSON. TypeScript stays the
reference until Android and the web leave Expo.

Nothing here is edited by hand except this file's prose and `push/`. Everything
else is generated by `npm run golden` and checked in CI by `npm run golden:check`,
which fails whenever the TypeScript engine changes without the corpus being
regenerated. The native CI job fails the other way round: when the corpus
changes and the port does not follow.

## Layout

| Path                                     | What                                                                                                    | Made by                                           |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| `transcript/golden/<suite>.json`         | every top-level call one transcript test file made into the engine, with its result                     | `packages/transcript/vitest.golden.config.ts`     |
| `transcript/golden-summary.json`         | per operation: calls recorded, replayable, skipped (by reason), whether it read a clock                 | `scripts/golden/generate.ts`                      |
| `transcript/fixtures/{events,rows}.json` | `packages/transcript/src/__fixtures__/{events,rows}.ts` as data                                         | `packages/transcript/golden/dump-fixtures.ts`     |
| `transcript/streams/<scenario>.json`     | a fake-gateway conversation: the frames it sent, the engine steps, the resulting state                  | `packages/fake-gateway/scripts/dump-frames.ts`    |
| `gateway/vectors/<module>.json`          | input/output vectors for the pure functions of `@hermie/gateway-client`                                 | `packages/gateway-client/scripts/dump-vectors.ts` |
| `markdown/<group>.json`                  | the Expo app's Markdown block structure per input: blocks, preprocessing, inline, streaming prefixes    | `scripts/golden/dump-markdown.ts`                 |
| `i18n/catalogue.json`                    | the Expo app's strings in en, nl and de, as text, lists or templates (`docs/i18n.md`)                   | `scripts/i18n/generate.ts`                        |
| `push/contract.json`                     | the push contract (category, actions, data keys, types, Android channels) — hand-written                | by hand                                           |
| `confirm-passkey/`                       | the passkey confirm contract: challenge construction, base-URL serialisation, CBOR subset, test vectors | the fork (`contract/confirm-passkey/generate.py`) |

`i18n/` has a pipeline of its own: `npm run i18n` writes it (with the Apple String
Catalog made from it) and `npm run i18n:check` guards it; `golden` leaves it alone.

## Regenerating

```sh
npm run golden         # rewrite every generated file under contract/ (and the counts below)
npm run golden:check   # regenerate into a temp dir and fail if contract/ differs
```

Both run the same pipeline: the transcript test suite under the recording config,
the fixture dump, the gateway vectors, the stream scenarios. Generation happens
in a temporary directory first, so a failed step never leaves `contract/` half
written, and the check never writes to it at all. Running `npm run golden` twice
in a row changes nothing: no timestamps, no absolute paths, no randomness, and a
stable file order.

When `golden:check` fails in CI, a change to `packages/transcript` (or to the
gateway client's pure functions, or to the fake gateway) changed observable
behaviour. If that was intended, run `npm run golden`, review the diff under
`contract/`, commit it, and port the change.

## Canonical JSON

Every generated file is the canonical value pretty-printed with two-space
indentation and a trailing newline. The indentation is for reviewers: a reader
must parse the file and compare canonical texts, never raw bytes. The canonical
text of a value is:

1. **Values.** Only `null`, `true`/`false`, numbers, strings, arrays and objects.
2. **Objects.** Keys sorted by UTF-16 code unit at every depth (JavaScript's
   default string sort; for the ASCII keys used here, plain byte order). A
   property whose value is `undefined` is **omitted** — an absent key and an
   `undefined` one are the same thing. `null` is a value and is kept.
3. **Arrays.** In order; an `undefined` element is written `null`.
4. **Numbers.** Finite only. Written as ECMAScript `Number.prototype.toString`
   writes them: integers without a decimal point or exponent (`1790000000000`,
   not `1.79e12`), `-0` as `0`, otherwise the shortest round-trip decimal with
   ECMAScript's exponent rules (`1e21`, `1e-7`). A port must not write `1.0` for
   `1`.
5. **Strings.** As `JSON.stringify` escapes them: `\"`, `\\`, `\b`, `\f`, `\n`,
   `\r`, `\t`, other code points below U+0020 as `\u00XX` with lowercase hex;
   everything else (including `/` and all non-ASCII) literal UTF-8. A string
   holding a lone UTF-16 surrogate is not representable and never appears.
6. **Whitespace.** None in the canonical text.

The reference implementation is `scripts/golden/canonical-json.ts`. Anything it
refuses (a function, `Map`, `Set`, `Date`, class instance, typed array, symbol,
bigint, NaN or ±Infinity, lone surrogate, cycle) is not JSON for this contract,
and a call that needs one is skipped (see the counts below).

## Replaying `transcript/golden/`

Each file is an array of tests in execution order:

```json
[{ "test": "describe name > test name", "calls": [{ "op": "applyEvent", "args": [...], "result": {...} }] }]
```

`<suite>` is the test file's name without `.test.ts`. Calls a file makes while
it is being loaded, outside any test (building a shared fixture state, say),
are grouped under the test name `(module scope)`. Only top-level calls are
recorded: a test's call into the engine is written down, the engine functions
it calls internally are not.

A call is self-contained: the engine state it ran on is one of its arguments,
so calls can be replayed in any order and independently of each other. For each
call:

1. Look up `op`. It is the name of a function exported from `@hermie/transcript`
   (every one is re-exported from its `index.ts`).
2. Decode `args` positionally. A **top-level `null` argument means "not
   supplied"** — `undefined` in TypeScript, the default value (usually `nil`) in
   the port. Arguments are complete: where a function takes a `now`
   parameter, the recorded call always carries it explicitly, even when the
   test relied on the `Date.now()` default.
3. If the call has a `now` field, the function read the clock itself (it has no
   `now` parameter); run it with the clock at that instant.
4. Call the function and compare:
   - `result` present: the canonical text of the port's result must equal the
     canonical text of `result`;
   - `result` absent and no `throws`: the function returned `undefined`
     (`Void`, or `nil` for an optional result — compare it as `null`);
   - `"throws": true`: the call must fail (throw / return an error). The error
     itself is not compared.

What the port must hold to: the same inputs give the same canonical output.
Item ids, `version` counters, `nextSeq`, the order of `order`, which keys are
absent — all of it is output and all of it is compared.

**Replayability is proven, not assumed.** The recorder encodes a call's
arguments to canonical JSON, decodes them again by the rules above, and runs
the real TypeScript function a second time on the decoded copy. Only a call
whose second run yields the identical canonical result (or throws again) enters
the corpus. Everything else is counted below, per operation and reason.

### The clock

The recording run pins the clock at **1790000000000** (2026-09-21T14:13:20Z).
These engine functions default a `now` parameter to `Date.now()`; every recorded
call to them carries `now` as an explicit argument, and the port should take it
as a parameter: `applyEvent`, `applyServerRequest`, `applyResumeSnapshot`,
`beginLocalTurn`, `beginSteer`, `confirmSubmit`, `markInterrupted`,
`applyProcessCompletion`, `applySubagentSnapshot`, `snapshotForCache`.

One function reads the clock **implicitly**, with no parameter to pass it in:
`activityEntries` computes its cutoff from `Date.now()` when
`options.sinceSeconds` is set. No recorded call sets `sinceSeconds`, so none
carries a `now` field today; should one appear, it will. The port should take
`now` as an explicit parameter there too. (This task does not change the
TypeScript engine; the counts below mark any operation that was observed reading
the clock during the run.)

### Skipped calls

A call is skipped when an argument or its result has no JSON form (the reasons
are prefixed `args:` / `result:`), or when the round trip changes its result
(`replay differs after a JSON round trip`). Today that is `exportTranscript` and
`previewFromChat` given callback options, `chatRowPreview` given a function,
and `contextUsageOf` given `Infinity`/`NaN`. Those behaviours are covered by the
TypeScript tests only; a port needs its own tests for them.

## Replaying `transcript/streams/`

One file per scenario: `plain-turn`, `tool-turn`, `approval`, `clarify`,
`subagents`, `reconnect-replay`. Each was produced by driving the fake gateway
over a real WebSocket exactly the way the app's chat controller does.

```json
{
  "scenario": "approval",
  "description": "...",
  "profile": "researcher",
  "pinnedNow": 1790000000000,
  "stepMs": 1000,
  "frames": [{ "connection": 1, "frame": { "jsonrpc": "2.0", "method": "event", "params": { ... } } }],
  "steps": [{ "op": "applyEvent", "args": [{ "type": "message.start", ... }, 1790000012000], "frame": 6 }],
  "checkpoints": [{ "after": 20, "label": "settled", "visible": { "quiet": [...], "normal": [...], "verbose": [...] } }],
  "final": { ...ChatState }
}
```

- `frames` is every frame the server sent to the recorded client, in arrival
  order. `connection` numbers the WebSocket (the reconnect scenario has two);
  `"rest"` marks an HTTP response body the client fetched instead.
- `steps` is every engine call the client made, in order, with **the current
  state left out of `args`**: each step's first parameter is the state the
  previous step produced, and its result becomes the next state. `frame` points
  at the frame that caused it. Two ops are not engine functions:
  - `createChatState` takes no state; its result replaces it (it is always the
    first step);
  - `patchState(fields, remove?)` is the store's own update: a shallow merge,
    `{ ...state, ...fields }`, then every key in `remove` deleted. It stands for
    the controller binding a runtime session and adopting the replay watermark.
  - `null` arguments mean "not supplied", as above; `now` is always explicit
    (the pinned instant plus `stepMs` per step).
- `checkpoints[i].visible` is `visibleItems(state, { level, showBotToBot: true,
showThinking: true })` for each level, taken after `after` steps.
- `final` is the whole `ChatState` after the last step.

A port replays `steps` from an empty state, compares each checkpoint's visible
items and the final state as canonical JSON. A port that also wants to test its
own wire decoding can derive the events from `frames` (an `event` frame's
`params` is the event) and check it arrives at the same `steps`.

The scenarios deliberately avoid races with the gateway's timers: ids and
epochs come from a seeded generator, the gateway's clock is pinned, and the
reconnect scenario disconnects while the chat is idle and lets a second device
run the turn it then replays (`session.events.since`) and folds in from the REST
tail. The `sessions.changed` tail sweep the app runs after an ordinary turn is
not modelled; the reconnect scenario's recovery sweep is.

## Replaying `gateway/vectors/`

Each file is an array of `{ "fn", "args", "result" }` (or `"throws": true`) for
one module of `@hermie/gateway-client` (plus `reconnectBackoffDelayMs`, from the
vendored `@hermes/shared`, which the backoff ladder is built on). Arguments
follow the same rules as the golden calls: positional, a `null` argument means
"not supplied", an absent `result` means the function returned `undefined`.

- A constant is written as a call with no arguments and `"note": "constant"`.
- Where an argument has no JSON form the entry's `note` says how it is
  encoded: bytes are lowercase hex strings, an error handed to a function is a
  plain descriptor (`probe-hints.json` describes the format), a `Set` result is
  a sorted array.
- `random` is the value `Math.random()` returned during the call (the backoff
  jitter, recorded as an input).
- A throwing entry may carry `error: { kind, message }` when the thrown value
  was a `GatewayError`; the kind is part of the contract, the message is there
  for a port that wants to match it too.
- A note starting `WHATWG quirk` marks a result that depends on a detail of
  the WHATWG URL parser (default ports, IPv4 shorthand, punycode, dot
  segments, opaque origins); a port built on another URL parser must
  reproduce these explicitly.

The script's header lists what is not recorded (classes, and functions that
need the network) and why.

## Replaying `markdown/`

Four files of cases, each an array of `{ "name", "input", "preprocessed",
"blocks" }`: `blocks` (every block kind), `inline` (emphasis, code, links,
tildes, mathematics), `preprocess` (the Hermes-specific rewrites) and
`streaming` (every prefix of three replies, cut at each line end and halfway
through each line). The inputs live in `scripts/golden/markdown-corpus.ts`;
`packages/markdown/src/contract.test.ts` replays the recorded files against the package.

`preprocessed` is `preprocessMarkdown(input)`, and a port compares it as a
string. `blocks` is what a renderer draws from it (`blockModelOf` in `packages/markdown`:
`splitBlocks`, then `marked.lexer` per block), in a neutral shape that does not mention marked:
`paragraph`/`heading` carry `inline`, a list its `ordered`, `start` (ordered
only) and `items` with `checked` (task items only) and `blocks`, a table its
`align`, `header` and `rows`, `code` its `language` and `text`, and `mermaid`
and `math` their source. `inline` is a list of runs `{ text, marks?, link? }`
with adjacent equal runs merged and line breaks as `"\n"`; `marks` is a sorted
subset of `bold`, `code`, `italic`, `math`, `strike`. The script's header
spells out every normalisation.

## `push/contract.json`

Hand-written: the notification category
`hermie.request` with actions `hermie.request.allow` / `hermie.request.deny`,
the data key `requestId`, the seven types, Android channel ids equal to the type
names, and the data payload's field list with types. It is the target every
sender and both app generations conform to; Hermie Web's and the Expo app's
tests check their payloads and ids against it.

## `confirm-passkey/`

A byte-identical copy of the fork's `contract/confirm-passkey/` (its `README.md`, `vectors.json`,
`generate.py` and `SHA256SUMS`): how a `confirm` request at level `passkey` binds its WebAuthn
challenge to the gateway, the request, the session, the text and the user, how a base URL is
serialised, which CBOR subset an attestation may use, and the vectors every verifier and every
client must pass. The fork is the source; this copy is refreshed by hand when the fork's changes,
and `shasum -a 256 -c SHA256SUMS` in that directory must pass. `golden` leaves it alone.

## Size

The whole generated corpus is about 13 MB in 45 files, 12 MB of it
`transcript/golden/` (full engine states in pretty-printed JSON; `duplicate-turns`
alone is about 5 MB). The streams are about 0.5 MB, the gateway vectors about
0.5 MB. That is under the 15 MB budget. If it grows past it, the
proposed trimming rule is: within one test, keep the first call of each
`(op, canonical args)` pair and drop exact repeats; then, if still too large,
write the golden files compact (one line) instead of indented — both preserve
everything a port replays.
