# Languages

Hermie's interface is **written in English**. Dutch and German are translations
of it, and that asymmetry is the design rather than an accident of which
language came first: every screen, every error and every hint is authored in
English, and a catalogue supplies another language for the strings somebody has
got to. A string with no translation paints the English sentence.

That rule is what lets a round add copy without stopping to translate it. It is
also why there is no "default language" setting that could leave a reader on a
half-translated screen with no way back: English is not a fallback of last
resort, it is the source.

## What a reader sees

**Settings → Appearance → Language** offers four rows:

| Row             | What it does                                               |
| --------------- | ---------------------------------------------------------- |
| _Follow device_ | Reads the device's own language every launch. The default. |
| English         | Pins English regardless of the device.                     |
| Nederlands      | Pins Dutch.                                                |
| Deutsch         | Pins German.                                               |

The three languages name themselves — never "Dutch", never "Niederländisch".
Somebody hunting for their own language is hunting for the word they use for it.

A device set to `nl-BE`, `nl_NL` or bare `nl` all land on Dutch: the region is
dropped, because Hermie has no Flemish copy and pretending otherwise would mean
three catalogues that are 99% the same. A device set to a language Hermie does
not speak gets English.

The choice belongs to the **device**, not to a gateway account — the same
argument light-and-dark makes in `store/settings.ts`. Somebody switching to
their work gateway and finding the app in another language would have found a
bug.

Switching takes effect **where the reader stands**. `App` subscribes to the
locale, which re-renders the tree under it; nothing is remounted, so a sheet
that was open stays open.

A device whose language Hermie speaks is in that language from the FIRST frame,
not from the first disk read — `store/language.ts` applies the device's answer
at module load, and the stored choice then either agrees or corrects it once.

## How it is built

| File                           | What it holds                                                          |
| ------------------------------ | ---------------------------------------------------------------------- |
| `src/i18n/locales.ts`          | Which languages exist; how a device tag folds into one.                |
| `src/i18n/active-locale.ts`    | The one language the app is speaking now, and who to tell on a switch. |
| `src/i18n/catalogue.ts`        | `localised()`, the `Translation<T>` type, and the coverage walkers.    |
| `src/i18n/use-locale.ts`       | `useFollowsLocale()` — the root's subscription.                        |
| `src/i18n/format.ts`           | `Intl` plurals, numbers, dates, relative times, list joins.            |
| `src/i18n/status-words.ts`     | The gateway's status enums per language.                               |
| `src/i18n/trees.ts`            | Every English string table, under its catalogue name.                  |
| `src/i18n/coverage.ts`         | What each language claims, and the allow-list.                         |
| `src/i18n/nl/`, `src/i18n/de/` | The catalogues, one file per English table.                            |

Each English table ends with one line:

```ts
export const strings = localised('app', stringsEn)
```

`localised` returns a proxy typed as the table it wraps, so a screen still
writes `strings.settings.language` and still gets a compile error when it
mistypes it. The read resolves **on access**: the catalogue is consulted, and
the English value wins when it has nothing to say.

### The thing that will bite you

A string table read at **import time** freezes the language the bundle loaded
with, which on a cold start is always English:

```ts
// Wrong. Painted in English for the life of the process.
const OPTIONS = [{ value: 'system', label: strings.settings.themeOptions.system }]

// Right. Rebuilt per render, which is what a switch needs.
const options = (): Option[] => [{ value: 'system', label: strings.settings.themeOptions.system }]
```

The same trap catches a `useMemo` or a `useEffect` that BUILDS text: its
dependency array has to carry the sentence, or it holds whatever language it was
first built in until its other dependencies happen to move. Depend on the
string, not on the locale — `useLocale()` in a dependency array is a value the
callback never reads, which the lint rule calls unnecessary and which explains
less than the string does:

```ts
const activeTitle = cronStrings.sections.active

const sections = useMemo(() => [{ title: activeTitle, data: active }], [active, activeTitle])
```

A `React.memo` is the third form of the same thing, and the one with no runtime
symptom at all: a memoised component whose props did not change is not
re-rendered, and a language switch changes nobody's props. **A memoised
component that reads `strings` subscribes itself**, with `useFollowsLocale()`.

If a screen keeps its old language after a switch, it is one of these three.

## Adding a language

1. Add the tag to `Locale` and `LOCALES` in `src/i18n/locales.ts`, and its own
   name for itself to `LANGUAGE_ENDONYMS`. The picker and the device detection
   both read those, so there is no third place.
2. Make `src/i18n/<tag>/`, one file per tree in `src/i18n/trees.ts`. Each file
   imports **only types**:

   ```ts
   import type { Translation } from '../catalogue'
   import type { cronStrings } from '../../features/cron/strings'

   export const cron: Translation<typeof cronStrings> = {/* … */}
   ```

   Types only, so `catalogue.ts` can import the catalogue without a runtime
   cycle back into the table it wraps.

3. Export them from `src/i18n/<tag>/index.ts` and add the tag to `CATALOGUES`
   in `src/i18n/catalogue.ts`.
4. Add the status words to `src/i18n/status-words.ts`.
5. Claim the trees in `TRANSLATED_TREES` (`src/i18n/coverage.ts`). The
   completeness test then holds the language to them.

Every key is optional, so a partial catalogue is a working catalogue from the
first line. What is **not** optional is the KIND of a key: a source key that
interpolates is a function, and the type refuses a bare string in its place —
otherwise a missing argument would be a sentence with a hole in it rather than a
compile error.

## Completeness, and the allow-list

`coverage.ts` holds two lists and the test (`__tests__/i18n-coverage.test.ts`)
reads both:

- **`TRANSLATED_TREES`** is the claim. A tree listed there must be answered in
  full, so a new English key fails the build until somebody translates it.
- **`UNTRANSLATED_KEYS`** excuses one named key at a time, as `tree.path.to.key`.
  It exists so a round can add English copy today and translate it next week
  without dropping the tree's claim.

The test also fails on a **stale** entry — a key that has since been translated
has to leave the list — and on a **stray** translation, which is what a key
renamed in English leaves behind.

Two kinds of entry belong in the allow-list permanently and are not a to-do:

- a string that is genuinely the same word in that language;
- a shell command, a config key or a URL. `hermes plugins install kanban` is
  typed into a terminal, and a terminal does not speak Dutch.

## Glossary

### Words that stay in English, in every language

These are the product's own vocabulary. A reader who translates them in their
head once has to translate them back the moment they open the gateway's own
dashboard, run `hermes skills list`, or read the Hermes documentation.

`gateway` · `bot` · `Bot Chat` · `Crons` · `Boards` · `Skills` · `MCP` ·
`push` · `token` · `handle` · `Kanban` · `OIDC` · `Hermes` · `Hermie`

Shell commands, configuration keys, file names (`MEMORY.md`, `USER.md`) and
placeholders that stand for something the reader typed are never translated.

## Length

Three surfaces have no room to grow, and a translation that overflows them is a
bug even when the words are right:

- **Tab labels** in the sidebar footer and the compact tab strip.
- **Segmented rows** (`ui/sheets/controls.tsx`): one row split evenly between
  its options, at 13pt semibold with `numberOfLines={1}`. Four options on a
  375pt-wide phone leave roughly 80pt each — which is why the language picker is
  a column of rows rather than a segmented control.
- **The chat header pill** and the popover rows, whose widths R2 and R4
  measured.

Keep those at or under the English length. Everywhere else — hints, footers,
error sentences — may run longer.

## Web client

The browser client (`native/web`, `@hermie/web-client`) speaks the same three languages with the same words.
It reads **the catalogue the Apple apps read** (`contract/i18n/catalogue.json`), through files `npm run i18n`
writes, and has one small table of its own for what only a browser says.

| File                                                    | What it is                                                              |
| ------------------------------------------------------- | ----------------------------------------------------------------------- |
| `native/web/src/generated/strings.ts`                   | the typed tree, `strings.app.common.cancel`; generated, never edited    |
| `native/web/src/generated/locales/{en,nl,de}.json`      | every key in that language, flat, one entry per line; generated         |
| `native/web/src/i18n/catalogue.ts`                      | builds the tree over the locale files; loads Dutch and German on demand |
| `native/web/src/i18n/template.ts`                       | renders a template (plurals, selects, lists) with `Intl.PluralRules`    |
| `native/web/src/i18n/locale.ts`                         | which language: stored choice, browser list, switching, `initLocale`    |
| `native/web/src/i18n/active-locale.ts`, `use-locale.ts` | the language in use, the subscription, `useLocale()`                    |
| `native/web/src/i18n/format.ts`                         | `Intl` plurals, numbers, dates, relative times, list joins              |
| `native/web/src/i18n/web-strings.ts`                    | strings only the web client has, in all three languages                 |
| `native/web/src/i18n/sheet-strings.ts`                  | the same, for what only a sheet or page loaded on demand says           |

`npm run i18n` writes the web files together with the Apple ones and `npm run i18n:check` fails when any of
them is stale. The Expo tables stay the source while Expo lives.

A locale file carries every key, and the client reads a small part of them. The production build bundles only the
keys the sources under `native/web/src` read (`native/web/scripts/catalogue-reads.mjs`): each read of `strings` is
followed through its static property accesses and the key or subtree it reaches is kept. A read the rule cannot
follow (the tree passed on whole, destructured, or read with a computed key at the root) keeps every key, so write
`strings.chat.approval.choices[id]`, not `strings[section]`. Tests and the dev server read the files whole.

### What a component writes

```ts
import { strings } from '../generated/strings'
import { webStrings } from '../i18n/web-strings'

strings.app.common.cancel // a string
strings.app.onboarding.stepCounter({ current: 2, total: 4 }) // a template: one object, named parameters
strings.app.bots.conversations({ count }) // plural selection happens inside
strings.cron.schedule.weekdayNames // a list
strings.chat.approval.choices[id] // a table keyed at run time: string | undefined
strings.app.layout.muteFor['1h'] // a key that is not an identifier
webStrings.language.followBrowser // a web-only string
```

The hierarchy is the TypeScript one, table name first. Every read resolves **when it is made**, in the
language that is active then, so the trap of the Expo app applies unchanged: text built at import time is
frozen in English (see "The thing that will bite you"). Read `useLocale()` once near the root, and in any
memoised component that reads strings; a switch then re-renders where the reader stands and nothing is
remounted.

A parameter that the TypeScript made optional is optional here; a list parameter is `readonly string[]`.
Templates are data (`{ "template": … }` in the locale file, the language of `scripts/i18n/template.ts`), and
`scripts/i18n/web.test.ts` holds the client's renderer to that file's reference over the whole argument grid.

### Which language

A browser has no per-site language setting, so the client has a picker (Settings, Appearance, Language) with
four rows: **Follow browser** (the default), English, Nederlands, Deutsch. The choice is stored in the
page's key-value store under `device.language` (so it survives a sign-out, like the colour scheme) and never sent to
a gateway; an earlier build's bare `hermie.language` is taken over once.

- A stored choice other than `system` wins.
- `system` reads `navigator.languages` **in order** and takes the first entry that is one of ours, with the
  region dropped: `nl-BE`, `nl_NL` and bare `nl` are all Dutch. This differs from a phone, which has one tag:
  a browser sending `fr-FR, nl` gets Dutch, because French is not ours and Dutch is the next thing it asked
  for. A list that names no language of ours gives English.
- A stored value that is not one of the four reads as "follow the browser".
- `initLocale()` runs before the first render, so a Dutch reader is in Dutch from the first frame. English is
  bundled; Dutch and German are separate chunks fetched then (or when the picker asks for them). If a chunk
  cannot be fetched the language in use stays and picking again retries.
- `<html lang>` follows the active language.

### Strings only the web client has

They go in `native/web/src/i18n/web-strings.ts`, each leaf written once with its three languages (or, when only a
sheet or page that loads on demand says it, in `sheet-strings.ts`, the same table kept out of the first load):

```ts
followBrowser: { en: 'Follow browser', nl: 'Volg browser', de: 'Browser folgen' }
```

A missing language is a compile error. `web-strings.test.ts` adds what a type cannot say: no empty text, no
Dutch or German that is a silent copy of the English (a word that really is the same goes in the test's
`SAME_AS_ENGLISH` list), and a function's placeholders present in every language. Anything the Apple apps
also say belongs in the Expo catalogue, not here, so the two cannot drift.

### Adding a language to the web client

`npm run i18n` writes a locale file for every language in the catalogue. Then add the tag to `Locale` and
`LOCALES` in `src/i18n/active-locale.ts`, its own name for itself to `LANGUAGE_ENDONYMS`, a loader to
`LOADERS` in `src/i18n/catalogue.ts` (the one place that names the chunk, so the bundler can split it), and
a line per leaf in `web-strings.ts`. The type checker and the tests find whatever is missing.

## Native apps

The native Apple apps (`native/`) speak the same three languages with the same
words, and for as long as the Expo app lives **the TypeScript catalogues stay
the source of truth**. Nobody translates a native string by hand: a change to
`strings.ts` or to `src/i18n/nl|de/` is exported to the native side by a script.

```sh
npm run i18n          # export and regenerate everything below
npm run i18n:check    # fail if any of it is out of date (CI runs this)
```

| File                                                                                 | What it is                                                                         |
| ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| `contract/i18n/catalogue.json`                                                       | every key, per language, as a plain string, a list or a template                   |
| `native/apple/HermieKit/Sources/HermieUI/Resources/Localizable.xcstrings`            | the String Catalog, written from the catalogue; what Xcode's editor shows          |
| `native/apple/HermieKit/Sources/HermieUI/Resources/<lang>.lproj/`                    | both catalogs compiled to `.strings` and `.stringsdict`: what the apps ship        |
| `native/apple/HermieKit/Sources/HermieUI/Generated/Strings.generated.swift`          | typed accessors over it                                                            |
| `native/apple/HermieKit/Tests/HermieUITests/Generated/StringSamples.generated.swift` | every key and argument combination, with what TypeScript renders, for `swift test` |
| `scripts/i18n/overrides.ts`                                                          | hand-written templates for the functions the export cannot read (one today)        |

All the generated files are rewritten together; never edit them.

The package ships the compiled `.lproj` files, not the catalogs, which
`Package.swift` excludes from its resources. SwiftPM compiles a catalog only with
its newer build engine (the default from Swift 6.4); the native build system,
the default up to Swift 6.3, copies it into the bundle unread, and every lookup
then returns its key. `scripts/i18n/compile-xcstrings.ts` does what
`xcstringstool compile` does, and a test holds the two to the same bytes on any
Mac with Xcode (and in the Native CI workflow), so the bundle is the same under
every toolchain and in the app builds.

### How a function becomes a template

A key whose English value is a function, like `onboarding.stepCounter`, cannot
cross to Swift as code, so the export **calls** it and writes down what it does.
It passes sentinel arguments and finds them in the output, which gives the
placeholders (`Step {current} of {total}`). It then probes:

- every number at 0 and 1. Where the sentence is not simply the number dropped
  into the generic one, the function has a singular (or zero) wording, and the
  template becomes a **plural** with `one` and `other` forms (and `zero` when
  the TypeScript has one). In the String Catalog that is a substitution with plural variations,
  which Foundation resolves with the language's own CLDR rules — for English,
  Dutch and German, `one` is exactly 1, the same as the `count === 1` the
  TypeScript writes.
- every string as `''`. Where an empty value does not simply drop out
  (`name || 'untitled'`, `description ? … : …`), the template becomes a
  **select** on `empty`. The String Catalog has no such thing, so the Swift
  accessor carries the `if` and each outcome is its own catalog key
  (`app.layout.removeFolder#name-empty`, `…#name-nonempty`).
- a list (`string[]`) with three items, which shows how it is joined; the
  separators become catalog keys of their own (`…#providers.separator`,
  `…#providers.last`), because they are words: `a, b or c`, `a, b of c`.

Every template, probed or hand-written, is then checked against the function it
came from over a grid of arguments — counts across the plural boundaries, empty
strings, a value with `%` and braces in it, lists of every length — and the
export refuses to write a catalogue that disagrees anywhere. The template
language itself is described at the top of `scripts/i18n/template.ts`.

The probes cannot see a function that compares two arguments with each other
(`chat.clarify.outcome`: `answered >= total`). That one is written by hand in
`scripts/i18n/overrides.ts`, which the export holds to the same check, so editing
the TypeScript function fails `npm run i18n` until the override says the same
again. An override for a function the probes can read is refused as stale.

### What a native view writes

```swift
Text(Strings.App.Common.cancel)
Text(Strings.App.Onboarding.stepCounter(current: 2, total: 4))
Text(Strings.Chat.Approval.Outcomes[choice] ?? choice)   // a table keyed at run time
```

The hierarchy is the TypeScript one, table name first; a branch is a type, a
string a static property, a function a static function with the TypeScript
parameter names as labels (`number` is `Int`, an optional string is `String?`).
Every read resolves when it is made, through `String(localized:table:bundle:)`
against HermieUI's own bundle, in the language the system picked for the app:
**the native apps follow the per-app language setting** and have no picker of
their own.

### Strings only the native apps have

They go in the second table, `Native.xcstrings`, next to the generated one, and
are written and translated by hand (in Xcode, or as JSON) in all three
languages. A string belongs there only when the Expo app has no counterpart;
anything both apps say goes in the TypeScript catalogues and arrives through the
export, so the two cannot drift. Read one with
`String(localized: "…", table: "Native", bundle: .module)`. Run `npm run i18n`
after editing it: that compiles it into `<lang>.lproj/Native.strings(dict)`,
which is what the app reads, and `npm run i18n:check` fails until you do.
